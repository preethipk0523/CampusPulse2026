Abstract

CampusPulse 2026 is a cloud-native prototype designed to demonstrate smart campus operations using Amazon Web Services. It receives simulated campus events, validates and processes readings, stores event records, calculates operational statistics, and identifies abnormal readings through a REST API. The implementation uses Amazon API Gateway, AWS Lambda, Amazon DynamoDB, AWS Identity and Access Management (IAM), Amazon CloudWatch, and AWS Serverless Application Model (SAM).

The prototype was deployed in the AWS Paris region (eu-west-3). Functional validation included automated unit tests, simulated event ingestion, API requests, statistics retrieval, alert retrieval, and inspection of CloudWatch logs. The project demonstrates how serverless services can be combined to implement a small cloud-based operational monitoring system while considering security, scalability, observability, and cost control.

Keywords: Cloud computing, AWS Lambda, API Gateway, DynamoDB, serverless, campus monitoring, event processing.

1. Introduction

1.1 Background

Universities operate classrooms, libraries, laboratories, and shared spaces that generate operational information. Occupancy levels, energy consumption, temperature readings, and equipment-related events can help campus staff understand the state of facilities and identify unusual conditions.

Collecting and processing this information manually can make it difficult to obtain timely operational visibility. Cloud services provide a way to receive events, process requests, store records, and make results accessible through an API.

CampusPulse 2026 is a prototype based on the smart campus scenario described in the Cloud Computing Final Project S2 2026 assignment.

1.2 Problem Statement

The project addresses the need for a lightweight system that accepts simulated campus readings, stores them persistently, provides basic statistics, and identifies readings that exceed configured thresholds.

The solution must also demonstrate a working cloud deployment, access control, monitoring, testing, and awareness of cloud costs.

1.3 Objectives

The objectives are:

  • Build and deploy a cloud-hosted REST API.
  • Accept simulated campus events from a Python script.
  • Validate and store events in Amazon DynamoDB.
  • Calculate basic operational statistics.
  • Classify abnormal readings as alerts.
  • Demonstrate administrator and operator roles.
  • Inspect backend execution logs using Amazon CloudWatch.
  • Test the implementation and document its limitations.
  • Apply cost-control practices appropriate for a small prototype.

1.4 Project Scope

The prototype supports simulated occupancy, energy, temperature, humidity, and maintenance event types, subject to the validation rules implemented in the backend.

The application exposes API endpoints for health checks, login, event submission, event retrieval, statistics, and alerts.

The current implementation is intended for academic demonstration. It does not provide a separate graphical dashboard or a complete production-grade security and disaster-recovery solution.

2. System Architecture

2.1 Architecture Overview

CampusPulse uses a serverless architecture deployed in the AWS Paris region (eu-west-3).

The main components are:

  1. Python event generator: Produces simulated campus readings.
  2. Amazon API Gateway: Provides the HTTP API entry point.
  3. AWS Lambda: Executes backend request handling, validation, event classification, and aggregation.
  4. Amazon DynamoDB: Stores campus event records in the CampusPulseEvents table.
  5. AWS IAM: Controls the permissions available to the Lambda execution role.
  6. Amazon CloudWatch: Collects Lambda execution logs.
  7. AWS SAM and CloudFormation: Package and deploy the serverless application.

2.2 Data Flow

The data flow is as follows:

  1. The Python event generator creates a campus event.
  2. The script sends the event to the /events endpoint through API Gateway.
  3. API Gateway invokes the Lambda backend.
  4. The backend validates the event and determines its severity.
  5. The event is stored in DynamoDB.
  6. Users with appropriate access can retrieve events, statistics, and alerts through the API.
  7. Lambda execution logs are available in CloudWatch for troubleshooting.

2.3 Architecture Decisions

The project uses managed serverless services to avoid maintaining a continuously running application server.

API Gateway provides a managed API entry point. Lambda executes backend logic when invoked. DynamoDB provides persistent storage and supports on-demand capacity. CloudWatch provides visibility into backend execution.

AWS SAM simplifies application packaging and deployment through an infrastructure template.

These choices are suitable for a small academic prototype. Production use would require additional security, recovery, performance, and operational controls.

4. Implementation

4.1 Backend

The backend is implemented in Python in app/main.py and deployed as an AWS Lambda function.

The application processes API requests, validates event fields, stores event records, calculates statistics, and returns abnormal events.

The Lambda function interacts with the CampusPulseEvents DynamoDB table. Its execution role supplies the required permissions for database operations.

4.4 Event Validation and Alert Classification

The backend validates required event fields, including building, room, event type, value, and unit.

The implemented rules classify occupancy above 80 people and temperature below 10°C or above 35°C as alerts. Energy readings above the configured threshold are also classified as alerts.

In the demonstration, the occupancy reading of 95 people and temperature reading of 38°C were classified as alerts. An earlier occupancy reading of 85 people was also returned as an alert.

These are simple threshold-based rules intended to demonstrate event processing. They are not a substitute for a production campus safety or building-management system.

4.6 Persistence

The DynamoDB table CampusPulseEvents stores the submitted event records. Each record includes an event identifier, building, room, event type, value, unit, severity, and timestamp.

The implementation uses a simple scan-based retrieval approach, which is acceptable for a small demonstration dataset but is not optimised for large-scale campus operations.

5. Security Design

5.1 Authentication and Authorization

The prototype implements two demo roles: administrator and operator.

The login endpoint authenticates a role using configured demo credentials and returns a bearer token. Protected endpoints use the token to determine whether the requested operation is permitted.

The administrator role can submit events and access protected information. The operator role has more limited access, according to the backend implementation.

5.2 IAM

AWS IAM provides the Lambda execution role and the permissions required for database operations. Permissions should follow the principle of least privilege.

The Lambda execution role should not receive unrelated administrative permissions.

5.3 API Protection

The deployed API is accessed through an HTTPS endpoint. The health endpoint is public, while protected operations require the appropriate bearer token.

Credentials and tokens must not be committed to source control or exposed in screenshots, logs, or presentation materials.

5.4 Security Limitations

The authentication implementation is designed for classroom demonstration and is not production-grade identity management. A production system should use a dedicated identity provider, stronger secret management, credential rotation, and more extensive authorization testing.

A custom VPC has not been configured. Consequently, the deployment does not demonstrate custom subnet and security-group segmentation.

These limitations are documented rather than presented as completed security features.

6. Scalability and Availability

6.1 Scalability

The architecture uses managed serverless services. Lambda can execute requests concurrently within the applicable account and service limits. API Gateway provides a managed interface, while DynamoDB on-demand capacity can accommodate changing workloads within its limits.

The current prototype uses simple event retrieval and aggregation. The scan-based approach may become inefficient as the dataset grows.

For larger deployments, improvements could include indexed queries, pagination, more efficient aggregation, load testing, and monitoring of service quotas.

6.2 Availability

Managed AWS services reduce the need to operate and maintain application servers directly. However, using managed services alone does not establish a complete high-availability strategy.

The prototype has not been tested under sustained heavy load and does not implement a comprehensive multi-region continuity design.

A production deployment would need explicit availability objectives, failure testing, and recovery procedures.

7. Cost Analysis and Cost Control

7.1 Cost Strategy

The project uses serverless computing and DynamoDB on-demand capacity to limit the need for continuously running infrastructure.

Potential cost drivers include API requests, Lambda invocations and execution duration, DynamoDB operations, and CloudWatch log ingestion and retention.

Actual charges depend on region, workload, account eligibility, applicable AWS pricing, and any credits.

The project also uses API responses to verify service health, event ingestion, statistics, and alert retrieval.

9. Disaster Recovery and Backup

Automated backups and a complete disaster-recovery system have not been implemented in this prototype.

The current system therefore does not guarantee recovery of stored records following accidental deletion, data corruption, or a regional failure.

For a production version, the following measures are recommended:

  • Enable an appropriate DynamoDB backup strategy.
  • Document database restoration steps.
  • Test restoration from backup.
  • Define recovery point objective (RPO) and recovery time objective (RTO).
  • Document recovery responsibilities and verify the recovery process periodically.

The current deployment has no formally established or tested RPO and RTO. These should be defined and measured before the application is used operationally.

11. Limitations and Future Improvements

The current implementation has the following limitations:

  2. No custom VPC configuration.
  3. No automated DynamoDB backups.
  4. No complete disaster-recovery process.
  5. No separate graphical dashboard.

  7. Limited load and performance testing.

Future improvements could include integrating a dedicated identity provider, implementing database backups and restoration testing, optimising database queries, developing a graphical dashboard, adding custom operational alarms, and conducting performance testing.

12. Lessons Learned

The project demonstrates how serverless AWS services can be combined to build a functional cloud-hosted API with persistent storage and basic operational analytics.

The implementation provided practical experience with event ingestion, Lambda execution, API Gateway integration, DynamoDB persistence, role-based access, automated testing, CloudWatch logs, and deployment through AWS SAM.

The project also demonstrates that a working prototype is not necessarily production-ready. Security, cost management, performance, backup, and recovery require independent validation.

One important lesson from testing was the need to compare aggregated API statistics with stored records instead of assuming that every returned metric is correct.

14. Conclusion

CampusPulse 2026 demonstrates a working serverless prototype for smart campus event processing. It accepts simulated events through an HTTP API, stores records in DynamoDB, calculates basic statistics, classifies abnormal readings, and exposes operational results through API endpoints.

The deployment uses AWS Lambda, API Gateway, DynamoDB, IAM, CloudWatch, and AWS SAM. The prototype was tested with six passing unit tests and four successful simulated event submissions. The API returned three alert records during the demonstration.

The project meets several important objectives of a cloud-based prototype, including event ingestion, persistence, API access, basic role-based access, and execution logging. Further work is required before production use, especially in identity management, backups, disaster recovery, performance optimisation, and validation of aggregated statistics.

The project provides a practical demonstration of serverless cloud architecture while documenting its limitations and opportunities for improvement.
